# OnO Bilibili Notifier（OnOBN）

> 中文名：**OnOB站通知订阅工具**　|　英文名：**OnO Bilibili Notifier**　|　缩写：**OnOBN**

一个跑在自己电脑上的 B 站更新提醒机器人：订阅的 UP 主**开播 / 投稿 / 发动态 / 发置顶评论**时，
自动往指定的 QQ 群推送提醒。自带一个网页管理面板，订阅、文案、图片、备份都在面板里点几下搞定。

> 🤖 **它是 [QQ 开放平台](https://q.qq.com)（腾讯官方机器人平台）机器人的程序**，
> 通过官方 SDK `qq-botpy` 走官方 WebSocket 网关与 REST API 收发消息。
> **不是** go-cqhttp / Mirai 之类的第三方协议实现，也不需要挂个人 QQ 号——详见下方「它是基于什么运行的」。

## 它是基于什么运行的

本项目是给 **QQ 开放平台（<https://q.qq.com>）机器人** 用的程序，不是通用 QQ 客户端插件。

| | 说明 |
|---|---|
| 运行方式 | 用官方 SDK **qq-botpy** 连接 QQ 开放平台，走官方 WebSocket 网关接收事件、官方 REST API 发消息 |
| 协议性质 | **官方接口**。不涉及任何逆向、模拟或非官方客户端协议 |
| 账号要求 | 在开放平台创建机器人，拿到 **AppID / AppSecret**；不需要挂自己的 QQ 号，也不会读取私人聊天 |
| 触达方式 | 机器人被拉进群后可向该群推送；也可以与用户单聊。群里 @ 机器人一句话即可自动登记该群 |
| 部署限制 | 官方接口有 **IP 白名单**、被动回复时效、主动推送频率等限制，放服务器时需按官方规则配置 |

> 换句话说：**这个项目不是"能发 QQ 消息的通用库"，而是一个已经接好官方机器人的成品程序**，
> 你只要填自己的 AppID / AppSecret 就能跑。

## 官方机器人 vs 第三方协议实现，差别在哪

在 QQ 上做机器人有两条完全不同的路线，外人很容易混淆，所以这里摊开讲。

### 差异点

| 维度 | **QQ 开放平台官方机器人**（本项目走这条） | **第三方协议实现**（go-cqhttp / Mirai / Lagrange 等） |
|---|---|---|
| 协议来源 | 腾讯**公开**的官方 API 与 WebSocket 网关，配官方 SDK `qq-botpy` | 社区**逆向**出来的客户端协议，模拟真实 QQ 客户端 |
| 用什么账号 | 在开放平台创建的**机器人**账号（独立 AppID/AppSecret） | **你自己的 QQ 号**，程序用它登录并长期在线 |
| 合规性 | 官方支持，符合平台规则 | 违反 QQ 用户协议，官方明确不认可 |
| 挂的是什么 | 一个机器人应用，跟你的私人号无关 | 你的个人号，被限制就全盘停摆 |
| 私家数据 | 机器人**看不到**你的私人聊天记录 | 你的号全程跑在程序里，消息理论上都经过它 |
| 能力范围 | 只做官方开放的事（群/单聊消息、指令面板、ark 卡片等） | 几乎等同真客户端：撤回、发语音、拉人、取全量群成员等 |
| 频率限制 | 官方频控明确（主动推送有配额、被动回复有时效） | 没有官方配额，但受客户端风控，发多了照样被限 |
| 网络要求 | 部分是 REST 接口，放服务器时要配**IP 白名单** | 一般只要能联网，无白名单要求 |
| 稳定性 | 接口由腾讯维护，变动会提前公告 | 协议一变就失效，得等社区跟进，期间可能完全不可用 |
| 上手成本 | 要注册开放平台、创建机器人（可能需审核） | 装好就能跑，无需申请 |

### 各自的优缺点

**✅ 官方路线的优点**

1. **合规、不封号**——最大的一条。不用担心哪天号没了。
2. **不用拿自己的 QQ 冒风险**——机器人是独立身份，跟你私人号解耦。
3. **不用追协议**——接口由官方维护，不用跟着版本更新疲于奔命。
4. **能正规上架**——审核通过后可对外提供服务，第三方方案做不到。
5. **隐私边界清楚**——它只能拿到你明确授权范围内的信息。

**❌ 官方路线的缺点（这些限制是真实存在的）**

1. **能力受限**——只能做官方开放的事。想撤回别人的消息、发语音、主动拉人、拉全量群成员，官方没给就没有。
2. **频控严格**——主动推送有配额，机器人多的群要留意；被动回复有时效，过期就不能再用那条引用回复。
3. **要申请、要审核**——不能下载下来立刻跑。
4. **放服务器要配 IP 白名单**——本机跑不用管，上云就得按官方规则填。
5. **消息格式有规范**——ark / embed / Markdown 都有固定结构，不能天马行空。

**✅ 第三方路线的优点**：能力几乎不受限、无需申请、生态成熟（NoneBot 等大量插件）、频率上没官方配额。

**❌ 第三方路线的缺点**：**有封号风险**（这是根本性的，且不可挽回）、要长期挂个人号、协议变动时会集体瘫痪、要处理滑块/设备锁/登录验证等一堆麻烦事。

### 本项目为什么选官方路线

它要做的事很单纯：**B 站有更新 → 往指定 QQ 群推一条消息**。这件事完全在官方能力范围内，
没有任何理由为此去冒封号的风险。所以本项目只对接官方，并且**不提供、也不打算提供**第三方协议支持。

> 如果你确实需要第三方方案才有的能力（撤回、取全量成员、发语音等），
> 本项目不适合你——请去看 [NoneBot](https://github.com/nonebot/nonebot2) 这类生态。

接口细节以 [QQ 机器人官方文档](https://bot.q.qq.com/wiki/) 为准；
能力边界调整、频控规则变化也以官方公告为准。

## 它能在什么时候提醒你

| 类型 | 说明 |
|---|---|
| 🔴 **开播** | UP 主直播间从"未开播"变成"直播中 / 轮播中" |
| 🎬 **投稿** | UP 主发布了新视频（按 BV 号判重） |
| 📝 **动态** | UP 主发了新动态（按动态 ID 判重） |
| 📌 **置顶评论** | UP 主在某条动态下置顶了评论 |

同一个 UP 主可以按群、按类型分别开关——比如"A 群只要开播提醒，B 群只要投稿提醒"。

### 不会重复打扰你

- **启动静默对齐**：每次启动先把所有订阅的当前状态记为基线，不会把订阅之前的历史内容翻出来推一遍。
- **删稿 / 撤稿不误推**：UP 主删掉最新动态后接口会"回退"到更早一条，程序能识别出来并保持静默。
- **置顶不重复推**：某条动态先按"新动态"推送过、后来被 UP 主置顶，不会再以"置顶动态"的名义推第二次。

## 安装

### 环境要求

- Python **3.8 或更高**（推荐 3.10+）
- Windows / Linux / macOS（再次提醒：只有 Windows 实测过）

### 步骤

```bash
# 1. 拿到代码
git clone https://github.com/XxBoLuoxX/OnO_Bilibili-Notifier.git
cd OnO_Bilibili-Notifier

# 2.（推荐）建个虚拟环境，别装进系统 Python
python -m venv .venv
# Windows:
.venv\Scripts\activate
# Linux / macOS:
source .venv/bin/activate

# 3. 装依赖
pip install -r src/requirements.txt
```

Windows 用户也可以直接双击 **`安装依赖.bat`**，它会自动完成上面的第 2、3 步。

## 配置

配置有**两条路**，选一条就行。**推荐用环境变量**，密钥不落盘，最安全。

### 方式一：环境变量 / `.env` 文件（推荐）

```bash
# 复制模板，然后填真实值
cp .env.example .env
```

编辑 `.env`：

```ini
ONOBN_APPID=你的AppID
ONOBN_APP_SECRET=你的AppSecret
ONOBN_BILI_COOKIE=            # 可选，B 站登录 Cookie
ONOBN_DATA_DIR=               # 可选，数据存放位置
ONOBN_PANEL_PORT=             # 可选，面板端口，默认 8088
ONOBN_PANEL_PASSWORD=         # 可选，面板访问口令
```

也可以不用 `.env`，直接设系统环境变量（部署时更常见）：

```bash
export ONOBN_APPID=你的AppID
export ONOBN_APP_SECRET=你的AppSecret
```

**优先级：系统环境变量 > `.env` 文件 > `config.yaml`。**
只要环境变量里配了，就以它为准，`config.yaml` 里那一份被忽略。

> ⚠️ `.env` **已被 `.gitignore` 排除**，不会进仓库。
> 提交前请用 `git status` 确认一遍——真密钥一旦推上去，改配置救不回来，
> 只能去 QQ 开放平台重置 AppSecret。

### 方式二：面板填写

启动后打开面板 → **🔐 凭据** 页面填写。填写的值会**加密后**存进 `config.yaml`
（密文 + 同目录的 `.machine_key` 解密钥匙）。
注意：这只能防"顺手打开配置文件看到明文"，**不是真正的加密保护**——
拿到 `.machine_key` 就能解开。真想万无一失，请用方式一。

### 去哪拿 AppID / AppSecret

1. 打开 [QQ 开放平台](https://q.qq.com)，用 QQ 扫码登录；
2. 创建一个**机器人**（不是"应用"，别选错）；
3. 进入该机器人 → **开发设置** → 复制 **AppID** 和 **AppSecret**；
4. 把机器人**拉进你要推送的 QQ 群**（在开放平台的机器人配置里完成邀请/上架流程后，
   群管理员把机器人加进群即可；具体以开放平台当时的规则为准）。

本地运行一般不需要配 IP 白名单；**放到服务器才需要**——把服务器公网 IP 填进开放平台的白名单。

> 文档以官方为准：<https://bot.q.qq.com/wiki/develop/api-v2/>

## 使用方法

### 启动

```bash
python src/start.py
```

Windows 用户双击 **`启动机器人.bat`** 即可。

启动后会自动打开面板：http://127.0.0.1:8088
（端口被占用时会自动往后找，实际端口看控制台输出。）

### 三步跑起来

1. **填凭据** —— 🔐 凭据 页面（或用上面的 `.env`）
2. **登记群** —— 在 QQ 群里 **@ 机器人说句话**，群就自动登记了；
   也可以去 订阅 → 登记群，手动粘群 ID
3. **加订阅** —— 订阅 → 添加订阅，填 UP 主 UID 或 B 站主页链接，勾选要提醒的类型

### 面板能做什么

| 页面 | 功能 |
|---|---|
| 📊 概况 | 运行状态、立即检测、最近动态、一键备份 |
| 📋 订阅 | 群与订阅管理、按 UP 主 / 合集反查群、订阅迁移 |
| 🔐 凭据 | QQ 凭据、B 站登录（浏览器登录 / 手动粘贴 Cookie） |
| ⚙️ 设置 | 通用、图片、提醒开关、数据与备份、安全、关于 |
| 📜 日志 | 运行日志（自动翻译成中文说明） |
| 🆕 更新日志 | 每个版本改了什么 |

### 数据存在哪

默认在**程序目录下的 `data` 目录**（配置、订阅、日志、备份、缓存、图片都在这）。
想换位置：设 `ONOBN_DATA_DIR`，或去 设置 → 💾 数据与备份 里改。

**整个 `data` 目录复制走就是完整备份**。面板里的「立即备份」也会打一份包。

> 历史提醒：v1.92.0 及更早的版本把数据放在程序目录内、且落盘有缺陷，
> 删除文件夹换新版会导致订阅丢失。**升级到本版本后不会有这个问题。**

## 常见问题

**Q：面板打不开？**
看控制台输出的实际端口（默认 8088，被占用会自动往后找）。
面板挂了会自动重新拉起；连续 3 次拉不起来会停下并提示。

**Q：机器人反复重启，提示"退出码 1"？**
崩溃原因会**直接打在控制台窗口**上，也会写进 `data/logs/crash.log`。
把那段内容贴给作者反馈即可。

**Q：订阅的 UP 主一直不推送？**
先去 概况 → 立即检测，看检测结果里"当前值"和"已记值"是否一致。
一致就是状态没变（正常，不会推送）；B 站登录态失效也会导致取不到数据，
去 🔐 凭据 用「🌐 浏览器登录」重新登录一次。

**Q：升级会不会丢订阅？**
v1.93.0 之后数据存放在独立数据目录、且每次改动立即落盘，删程序文件夹换新版不会丢。
如果你在用更早的版本，**先备份 `data` 目录**再升级。

## 维护政策

本项目已趋于稳定，此后**只接受两类改动**：

1. **功能更新** —— 新增能力，或对已有能力的实质性增强；
2. **严重 bug 修复** —— 导致程序无法启动、数据丢失/损坏、推送完全失效、
   安全凭据泄露，或其他「不用就没法正常用」的问题。

除上述两类之外，一概不再改动，包括但不限于：

- 措辞、文案、提示语的微调
- 界面配色、间距、字号、动画等纯观感调整
- 代码风格、命名、注释、目录结构的整理
- 性能优化（除非慢到明显影响正常使用）
- 新增测试（除非是为了验证上面两类改动）

**为什么这样定**：这个项目由 AI 生成代码、作者一人维护，每一次改动都要
重新跑全量回归、重新打包、重新验证，成本远高于改动本身。把改动收窄到
「真正影响使用」的范围，才能保证每一次发布都是可靠的。

如果你想自行修改，完全欢迎 —— MIT 许可允许 fork 和修改，只需保留署名。
提交 Issue 时如果属于上述两类，请说明**具体影响**（比如「点了备份之后
面板一直转圈」），比「建议优化一下」更容易被处理。

## 反馈

有 bug 欢迎提 Issue。反馈时最好带上：

1. **版本号**（设置 → ℹ️ 关于 → 「📋 复制版本信息」，一键复制）
2. **操作过程**：点了什么、期望什么、实际发生什么
3. **日志末尾的报错**（日志页可看，或 `data/logs/bot.log`）

⚠️ 截图时请给 **群号、AppSecret、Cookie** 打码。

按维护政策，**只有属于「功能缺失」或「严重 bug」的反馈才会触发新版本**。
提 Issue 时请说明**具体影响**（例如「点了备份之后面板一直转圈，备份没生成」），
比「建议优化一下」更容易被处理。纯观感、措辞、代码风格类建议会被标记为
`wontfix` 并关闭 —— 不是不重视，是维护成本所限，还请理解。
